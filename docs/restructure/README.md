# Реструктуризация кода entWatch

Структурный рефакторинг: код раскладывается по модулям и папкам, поведение плагина не меняется.
Папка — рабочие документы процесса. Когда процесс закончен, итоговая раскладка переносится
в `CLAUDE.md` проекта (раздел «Subsystems»), а папка остаётся историей решений.

| Файл | Что в нём |
|---|---|
| `README.md` | цель, решения владельца, правила, проверка — этот файл |
| `inventory.md` | как код устроен сейчас: роли файлов, смешанные обязанности, межфайловые зависимости |
| `target.md` | целевая раскладка, контракт подсистемы рестриктов, порядок include'ов |
| `plan.md` | этапы и шаги: что, откуда и куда переносится, чем проверяется |
| `prompt.md` | промпт для агента, который выполняет план |
| `tools/symbols.py` | механическая проверка «только перенос» без компилятора |

## Зачем

Код разбит на файлы, но у подсистем нет границ. Главный пример — рестрикты: путь загрузки
рестрикта лежит в `client.sp`, меню рестриктов — в `admin_menu.sp` (и читает поля `Restricts[]`
напрямую), соединение с базой — в отдельном `database.sp`, хотя кроме рестриктов база никому
не нужна. Попытка выключить встроенную систему define'ом потребовала `#if` в шести файлах.

Цель — чтобы у каждой подсистемы была граница: её внутренности лежат в её файлах, остальной
плагин обращается к ней через несколько функций. Конкретно для рестриктов — чтобы
реализацию можно было заменить (встроенная база, RestrictCore, никакой), поменяв один файл.

## Решения владельца

Приняты в обсуждении 2026-09-28; не пересматривать.

1. **Встроенная система рестриктов остаётся** — своя база `ebans` плюс временные рестрикты,
   за define'ом `RESTRICT_BUILTIN` (включён по умолчанию, то есть продакшн не меняется). Нужна,
   чтобы можно было вернуться к ней после перехода на RestrictCore. Имя define'а выбрано
   в этом процессе; если владелец захочет другое — меняется в одном месте (`modules.sp`) и
   в `restrict.sp`.
2. **Интеграцию с RestrictCore делает владелец сам**, после рефакторинга. Define для неё
   и её реализацию (`restrict/core.sp`) агент **не** пишет. Рефакторинг только готовит место:
   контракт подсистемы и выбор реализации в `restrict.sp`.
3. **`modules.sp`** — все define'ы модулей в одном файле и `ModulesInit()`, которую зовёт
   `OnPluginStart()`, — по образцу RestrictCore.
4. **Меню рестриктов принадлежит рестриктам**: оно переезжает в папку встроенной системы и
   исчезает вместе с ней.
5. **Сначала чистый рефакторинг, потом интеграция.** Черновик с `//#define DATABASE`
   (незакоммиченные правки шести файлов на `master` и неотслеживаемая папка
   `entWatch/restrict/`) **удаляется насовсем** — это шаг 0 плана. Рефакторинг идёт от
   закоммиченного `master` в ветке `refactor/structure`; первый коммит ветки — эта папка.
6. **Агент не компилирует и не собирает.** Компилирует владелец. Замену компилятору даёт
   `tools/symbols.py` (см. ниже) и чтение кода.
7. **Масштаб — весь плагин, по порядку**: `modules.sp` → рестрикты → админ-меню → конфиги и
   предметы → медиатор. Каждый этап заканчивается рабочим, компилируемым плагином.
8. **Коммитит агент — после «ок» владельца на каждый шаг.** Шаг → дифф и отчёт → стоп →
   владелец отвечает → коммит → следующий шаг. Пуш — только по отдельной просьбе.

## Правила

Правила из `CLAUDE.md` проекта действуют полностью. Поверх них для этого процесса:

- **Только перенос.** Текст функции, глобальной переменной, define'а, комментария переезжает
  побайтно (отступы — как в исходном файле). Не переименовывать, не переформатировать,
  не «заодно поправить», не добавлять `static`, не менять `#pragma`. Найденный по дороге
  дефект записывается в отчёт шага, код не трогается.
- **Изменение, которое не перенос, заранее названо в `plan.md`** (новая функция фасада,
  вызов вместо вставки, новый `#if`). Всё, чего в плане нет, — стоп и вопрос владельцу.
- **Порядок вызовов сохраняется.** Если шаг переставляет вызовы (например, `ModulesInit()`),
  в плане записано, почему перестановка безопасна. Своих перестановок агент не делает.
- **Каждый шаг компилируется во всех сочетаниях define'ов.** Глобальные переменные,
  define'ы, типы и константы enum в SourcePawn видны только после объявления, функции —
  везде. Поэтому файл модуля сначала объявляет свои глобальные переменные и define'ы,
  потом подключает файлы своей папки, потом определяет свои функции.
- **SQL — `#define` в файле, который выполняет запрос** (как в RestrictCore).
- **Публичный API не меняется**: 8 нативов, 6 форвардов, структуры `Config`/`Item`.
  Натив регистрируется во всех сборках, даже если в какой-то сборке ему нечего вернуть.
- **Шаг — не больше пяти изменений**, потом дифф владельцу и стоп. «Изменение» здесь —
  одна группа символов, перенесённая в один файл, или одна правка из плана.
- **Git.** Всё, что разрешено, перечислено в шаге 0 и в «Как выполнять шаг» (`plan.md`):
  удаление черновика, ветка `refactor/structure`, коммит после «ок» владельца. Сообщения —
  Conventional Commits на английском (`refactor: …`, `docs: …`). Не пушить, не делать
  `git clean` шире указанного пути, не переписывать историю (`--amend`, `rebase`, `reset`).
- Новые файлы — UTF-8 без BOM. Переводы строк нормализует git (`core.autocrlf=true`).
  Комментарии — на русском, в стиле соседнего кода.

## Проверка без компилятора

`tools/symbols.py` прогоняет упрощённый препроцессор по `entWatch.sp` для всех 128 сочетаний
define'ов (`BOTOX_SM`, `HUD`, `ASSIST_USE`, `ADMIN_MENU`, `HALFZOMBIE`, `RESTRICT_BUILTIN`,
наличие zombiereloaded), разбирает единицу трансляции на символы верхнего уровня и сравнивает
базовую ревизию с рабочим деревом:

- каждый символ есть в тех же сборках и с тем же текстом (с комментарием над ним, пробелы
  нормализованы) — иначе «удалён», «добавлен» или «изменён текст»;
- ни одна глобальная переменная, define, тип или константа enum не используется раньше
  объявления — иначе «использование раньше объявления»;
- ни один символ плагина не используется в сборке, где его нет (например, сборка без
  `RESTRICT_BUILTIN` зовёт функцию встроенной системы) — иначе «используется символ,
  которого нет в этой сборке».

```
python docs/restructure/tools/symbols.py                         # HEAD против рабочего дерева
python docs/restructure/tools/symbols.py --allow ClientAuth       # изменение из плана
python docs/restructure/tools/symbols.py --fix RESTRICT_BUILTIN=1 # только сборки с define'ом
python docs/restructure/tools/symbols.py --verbose                # в каких сборках расхождение
```

Код выхода 0 — только перенос (плюс разрешённое `--allow`). Самопроверка: `--work HEAD`
даёт ноль расхождений; на искусственно переставленных include'ах скрипт ловит `DBLoaded`,
использованный в `ClientAuth` до объявления; без `restrict.sp` в сборке — 26 обращений
к пропавшим функциям рестриктов. Полный прогон — около 20 секунд.

Ограничения: это не компилятор. Разбор приблизительный, типы и сигнатуры не проверяются,
внутренности функций не анализируются, предупреждения компилятора (неиспользуемые символы)
не видны. Поэтому в отчёте шага: «проверено скриптом и чтением» — не «проверено компиляцией».
Define `RESTRICT_CORE` (интеграция с RestrictCore, 1.2.0) добавлен в `TOGGLES`: теперь
перебирается 256 сочетаний.

## Продолжение без пауз

2026-09-28 владелец разрешил выполнить оставшиеся шаги и коммитить их без ожидания
отдельного одобрения. Границы рефакторинга и проверки каждого шага сохраняются;
компиляция, запуск сервера, интеграция RestrictCore и пуш не выполняются.
