# entWatch — состояние работы по итогам аудита

Ветка `fix/audit-batch-1` от `master`. Версия `myinfo` поднята **1.0.1 → 1.0.2**.
Полный отчёт аудита — `AUDIT.md` (107 находок). Этот файл — что с ними сделано.

## Договорённости с заказчиком

1. Правки **строго хирургические**: меняются только строки, относящиеся к дефекту.
   Соседний код (тернарники, отступы, порядок объявлений) не трогается.
2. Код пишется **понятно**: явные ветки вместо тернарников, именованные локальные
   переменные, комментарии по-русски. Логи и строки сообщений — по-английски, как в проекте.
3. Стиль проекта важнее `~/.claude/rules/sourcepawn.md` там, где они расходятся.
4. Компилирует **ассистент** после каждого батча (`spcomp` 1.13.0.7202), 0 ошибок / 0 предупреждений.
5. Батчи по ≤5 изменений, после каждого — дифф и коммит. «Дальше» = коммить и продолжай.
6. Старые записи в `ebans` с перепутанными `pname`/`aname` **не мигрируем** — чиним только код.
7. Сборочные проблемы (`REEQUIRE_PLUGIN`, HALFZOMBIE без ZR, `#warning`) — **не трогать**.
8. Мёртвый код помечается, а не удаляется. Исключение — Protobuf-ветка: её удаление
   значилось в планах в CLAUDE.md.

## Поправки к AUDIT.md, найденные по ходу работы

Эти находки отчёта **неверны**, чинить нечего:

- **Цепочки сравнений в SourcePawn работают правильно.** `0 < duration < 525600` — это конъюнкция,
  а не `(0 < x) < N`. В компиляторе есть `ChainedCompareExpr`: `parser.cpp:750`,
  `semantics.cpp:1050`, `code-generator.cpp:1005`. Это же опровергает правило в
  `~/.claude/rules/sourcepawn.md` — его стоит поправить, иначе оно и дальше будет
  плодить ложные находки.
- **`%N` с индексом 0 печатает `"Console"`**, а не бросает ошибку (`sprintf.cpp:1192-1196`).
  Находки про `%N` с админом-консолью в `sm_espawn`/`sm_etransfer`/`LogAction` — ложные.
- **`HookSingleEntityOutput` дедуплицирует** одинаковые (функция + entity ref) —
  `outputnatives.cpp:75-82`. Двойной учёт use через compare/relay невозможен.
- **`SDKHooks::Hook` НЕ дедуплицирует** — `extension.cpp:792-796`. Повторная регистрация
  `SDKHook_Use` на одной сущности реальна и удваивает вызов.
- **Инвариант «владелец предмета жив»** заявлен заказчиком как правило дизайна. Значит
  `GetClientTeam(Items[].Owner)` в `Timer_Hud` и `chat.sp` — корректный код, защищать его
  не нужно; падение там было бы сигналом о нарушении инварианта в другом месте.
  Игра сама удаляет нож при смерти и смене команды, поэтому сущность оружия исчезает и
  предмет снимается с учёта через `ItemsOnEntityDestroyed`.

## Решения заказчика по оставшимся вопросам — ВЫПОЛНЕНО в `5b7de8a`

1. **C2 — вариант А.** `ItemsOnMapStart()` сканирует только при `Late`. Дополнение,
   найденное при пересчёте: в обычной ветке нужен `ItemsClear()` + `RoundStarted = false`,
   иначе учёт прошлой карты живёт до первого `round_start` (перед сменой карты
   `round_end` бывает не всегда), а `Items[].Config` к тому моменту уже указывает
   в конфиги новой карты.
2. **Редактор конфигов** — один на сервер, занятость выводится из
   `AdminConfigEditorGet()` (скан `EditClientsConfigs[].IsEdit()`), `EditedConfigs[]`
   удалён, добавлена фраза `Config editor is busy`. Блокировка сама снимается на
   выходе игрока: SourceMod отменяет его меню (`MenuStyle_Base.cpp:202`,
   `_CancelClientMenu(client, MenuCancel_Disconnected, true)`), а `MenuAction_Cancel`
   уже чистит состояние.
3. **Индексы в меню** — заказчик отказался от `unique_id`, принят вариант со ссылкой
   на сущность оружия: `ItemGetRef()` / `ItemsGetByRef()` в `items.sp`, три меню
   (`TransferByMapMenu`, `TransferByTargetMenu`, `UseItemsMenu`) кладут в info-строку
   ссылку. API не тронут.
4. **Half-zombie** — `ZR_OnClientInfected` (post) вместо `ZR_OnClientInfect` (pre).
5. **Луч в `AssistUseIsValidTarget`** — `RayType_EndPoint`, `ASSIST_USE_DISTANCE`.
   Изначально 96 (80 + 20%), по решению заказчика поднято до **128**: промах в
   меньшую сторону хуже, чем в большую (не распознав настоящую кнопку, модуль
   нажмёт её вместе с материей). Значение подбирается практикой, не расчётом.

### Факты из движка (получены с прямого разрешения заказчика)

- `PLAYER_USE_RADIUS = 80.f` — `hl2_src-leak-2017/src/game/shared/baseplayer_shared.h:15`.
- `CBasePlayer::FindUseEntity()` — `baseplayer_shared.cpp:1096-1132`: прямой луч летит на
  1024 юнита (`searchCenter + forward * 1024`), но попадание принимается только при
  `dist < PLAYER_USE_RADIUS`; боковые hull-трейсы вниз — 72 юнита. Итог: реальная
  досягаемость прямого `+USE` — **80 юнитов**.

### Пункт 3 — три варианта, цена каждого

- **Ссылка на сущность оружия** (`EntIndexToEntRef` в info-строке меню,
  `ItemsGetByWeapon(EntRefToEntIndex(ref))` в обработчике). Нового состояния ноль,
  функция поиска уже есть, протухшая ссылка сама даёт `-1`. **Рекомендация.**
- **`unique_id` полем в `Item`.** Чисто, двигается вместе со структурой при сдвиге
  массива — но `Item` копируется наружу нативом `entWatch_GetItem()` с проверкой
  `sizeof`, то есть **все плагины-потребители придётся пересобрать**, и это MINOR-версия.
- **`unique_id` параллельным массивом.** API не ломает, но массив надо сдвигать в
  `ItemRemove()` синхронно с `Items[]` — ровно тот класс ошибок, который мы весь аудит
  и чинили.

## Итог противосостязательной проверки (все 107 находок имеют статус)

Оставшиеся 12 находок прошли отдельный прогон судей (`opus`, `effort: high`,
по одному на файл). Результат:

- **Убиты — заявка была неверной**: №54 (`prevButtons` самоочищается на первом же
  usercmd без `IN_USE`), №62 (форвард стреляет там, где `Items[]` пуст по замыслу —
  триггер не пишется), №76 (`SteamIdToLocal` первым оператором пишет сентинел
  `STEAM_ID_STOP_IGNORING_RETVALS`, пустым `SteamID` остаться не может —
  `smn_players.cpp:354`).
- **Понижены до «правки не стоит»**: №40 (`mp_restartgame` — отказ в закрытую
  сторону, хуки переживают `ItemsClear()`), №49 (`CRotButton::Spawn` принудительно
  ставит `m_flWait = 1`, `buttons.cpp:883-884` — заявленный триггер невозможен),
  №53 и №70 (косметика).
- **Исправлены**: №95, №3, №68.
- **№5 / №23 — решение владельца: игнорировать.** На сервере нет стим-валидации,
  `GetSteamAccountID()` всегда результативен, поэтому триггер недостижим. Это
  согласуется с находкой судьи: `CPlayer::IsAuthStringValidated`
  (`PlayerManager.cpp:2345-2352`) возвращает `true` на LAN-сервере. **Если сервер
  когда-нибудь переедет на стим-авторизацию — находку поднять заново**: `ClientAuth`
  выходит по `return` без выставления `Authorized`, повторить некому, игрок до конца
  карты без права подбора. Саму проверку `!Account → не слать запрос` при этом
  трогать нельзя: `pid = 0` — ключ IP-онли банов.

## Осталось

Все находки аудита, принятые к исправлению, закрыты. Не сделано намеренно:

- `OnTriggerTouch` подавляет `EndTouch` — заказчик: оставить как есть.
- Сборочные проблемы (`REEQUIRE_PLUGIN`, HALFZOMBIE без ZR, `#warning`) — не трогать.
- Мёртвый код (помечен, не удалён): `ItemsGetByName`, `ConfigGetByName`, `ConfigGetByNames`.
- Дубли ключей в `entWatch.phrases.txt` (`Map`, `Unban item`) — существовали до работы,
  не трогались.

Из планов CLAUDE.md остаются: редизайн схемы `ebans` под веб-панель, постепенный
переход на `~/.claude/rules/sourcepawn.md`.

**Сделано сверх аудита:** временные рестрикты — до ближайшей смены карты
(версия 1.1.0). Источник истины — список аккаунтов `TempRestricts[]` в
`restrict.sp`; в базу не попадает и потому работает при недоступной базе. Ключ по
аккаунту, поэтому перезаход игрока рестрикт не снимает.

Горячий путь читает кэш `Restricts[].Temporary`, а не список: `RestrictClientHasRestrict()`
зовётся с `SDKHook_Touch`, то есть каждый тик на каждого игрока в триггере
(`items.sp:196`), и прочёсывание массива на 64 элемента там недопустимо. Кэш
пересевается в `ClientAuth` (единственное место, где становится известен аккаунт),
выставляется при выдаче, снимается при снятии и обнуляется в `RestrictOnMapEnd()`.

Сброс привязан к `OnMapEnd`, а **не** к `OnMapStart`: кнопка Reload в `sm_eadmin`
зовёт `OnMapStart()` руками, и на старте сброс молча стирал бы все временные
рестрикты посреди карты.

Выдача: `sm_eban <игрок>` без второго аргумента либо седьмой пункт в меню
длительности. Снятие: `sm_uneban` — временный снимается без обращения к базе,
и на этом команда заканчивается; если у игрока есть ещё и рестрикт из базы (такое
состояние создаёт только `sm_addeban`, он не смотрит в список), админу говорится
повторить команду.
